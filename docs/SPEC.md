# Syla Runtime Receipt v0.1

Status: **developer preview**

## Purpose

A Syla Runtime Receipt is a portable record of the costs, resources, and observable outcome of one agent run. It can aggregate provider usage, tools, retries, evaluations, and payments without requiring those systems to share a billing API.

## Top-level shape

```json
{
  "specVersion": "syla.execution-receipt/0.1",
  "execution": {},
  "events": [],
  "outcome": {},
  "economics": {},
  "proof": {}
}
```

## Run metadata

Required:

- `id`: run identifier generated by the recorder or caller.
- `agentId`: caller-defined agent/workflow identifier.
- `task`: short description of intended work.
- `startedAt`: ISO-8601 timestamp.
- `endedAt`: ISO-8601 timestamp after finalization.

Optional `traceId` and JSON-safe `metadata` may correlate the receipt to an observability system. Avoid secrets and sensitive prompt content.

## Event types

### `model.usage`

Describes one model usage event. Fields include provider, model, token counts, request ID, and optional cost.

### `tool.usage`

Describes one tool/resource operation and optional direct cost.

### `payment`

Describes a settlement or payment reference. `protocol` is typically `x402` but may be another rail. Payment events can include network, scheme, payer/payee, resource, and transaction identifier.

A payment event does not replace the underlying protocol's proof. It links that proof into the broader runtime record. `amount` records the actual settlement asset; optional `cost` records the economic valuation used in receipt totals when that asset differs from the receipt's base currency.

### `retry`

Marks recovery work. Optional cost can be used to compute `recoveryCost`.

### `evaluation`

Records an evaluator name, metric, score from 0 through 1, and optional pass/fail.

### `custom`

Namespaced escape hatch for experimental events. Consumers must not assume custom data semantics.

## Money

```json
{ "amount": "0.00125", "currency": "USD" }
```

Amounts are non-negative base-10 decimal strings. Implementations must not sum them with binary floating point.

The v0.1 economics summary uses a single currency per receipt. Mixing currencies throws during finalization. Currency conversion belongs outside the core receipt.

`paymentCost` is included in `totalCost` by default. For payment events, economics uses `cost` when supplied and otherwise uses the settlement `amount`. Applications should not also record the same purchase as a tool cost, otherwise they will double-count it.

## Economics

- `modelCost`: sum of model event costs.
- `toolCost`: sum of tool event costs.
- `paymentCost`: sum of payment events.
- `recoveryCost`: sum of retry event costs.
- `totalCost`: model + tool + payment + recovery.

Evaluation events do not directly affect economics.

## Proof

The v0.1 integrity check detects receipt changes; it does not authenticate who created the receipt.

1. Remove the top-level `proof` property.
2. Recursively serialize objects with keys sorted lexicographically.
3. Preserve array order.
4. Serialize JSON primitives using ECMAScript `JSON.stringify` behavior.
5. Hash UTF-8 bytes with SHA-256.
6. Encode the lowercase hexadecimal digest as `sha256:<hex>`.

Proof shape:

```json
{
  "algorithm": "sha256",
  "canonicalization": "syla-json-v1",
  "digest": "sha256:...",
  "createdAt": "..."
}
```

Because `syla-json-v1` is repository-defined, v0.1 receipts should not claim language-independent standards compliance. A future stable version should adopt or formally specify canonicalization across languages.
